# 合成移植复审与 PR 范围

复审日期：2026-11-03。原版比较基线为 `67d12a906951db0e11d65e394ca44b0dac5e689f`，初始移植为 `0604d4d641b17aec2b43c677d709c6424633b92f`。最终复审同时检查了原版到当前树的全部差异、初始移植后的修复、未跟踪的新文件及暂存区。原快照保留，修复集中在 `codex/craft-warehouse-integration`。

## 范围分类

| 类别 | 处理方式 |
| --- | --- |
| 合成移植缺陷 | 本 PR 修复：请求、规划、物品分配、预留、转换结算、回库、恢复、调度、默认测试 |
| 原云仓共享边界影响合成 | 本 PR 以合成保护条件接入：严格取存证据、pending 写保护、启动迁移保护、残留归属保护 |
| 原云仓普通取存和潜影盒行为 | 单独处理。本 PR 不宣称完成这部分全面修复；原有测试继续运行 |
| 新能力 | 盒内取料、采集、熔炼、切石、锻造及新的收费规则不在当前合成范围 |

原云仓的普通转移帮助函数可能只凭客户端预测报告移动；本次实测复现了这种条件。合成调用增加严格服务端核验，普通存取默认行为仍沿用原版。这是需要单独处理的既有问题，不能把合成路径的严格模式当作所有云仓转移均已修复。

未知盈亏归属 `momo`、潜影盒拆装与普通存取恢复属于原云仓已有规则和实现，不能仅因与合成不同就一概列为已证实错误。本次保证仍有合成 journal 的资产不会被这些通用流程接管。

## 最终链路与职责

```mermaid
flowchart LR
  A[管理员请求与明确 owner] --> B[独占开工并重规划]
  B --> C[精确 itemKey 预留与 journal]
  C --> D[Warehouse 严格取料]
  D --> E[单次标准配方合成]
  E --> F[服务端证据确认]
  F --> G[SQLite 原子转换与流水]
  G --> H[Warehouse 严格回库]
  H --> I[下一触发或完成]
  D --> J[不确定状态保留预留]
  E --> J
  H --> J
  J --> K[原 botId 服务端恢复核对]
```

Olela 保留配方图、库存优先、多步拓扑和分支规划能力。实物执行收敛到云仓自己的 `Warehouse`；`ItemCatalog` 负责完整组件/NBT 身份；`CraftLedger` 使用同一个 `StoreDb` 连接管理预留、转换、流水及恢复。原 Olela 的 HTTP 交付、专用 buffer/output、depositOperation 和独立寻路执行器已删除，避免维持两套仓储事实。

### 请求、规划与归属

- 中文名称和别名先经云仓目录解析。仅管理员可用；队列保存明确 owner 和目标，开工时重新检查权限、成员身份和可用库存。
- 数量为仓库最终目标总量，已有成品抵扣缺口；超出配方整数倍时保留实际多产出的成品。拒绝零、负数、小数及不安全整数。
- 生产配方来自 `minecraft-data(server.version)`。历史 `recipes.json` 用作上游回归夹具，不补进生产配方图。1.21.4/1.21.11 的差异、新铜制配方及模板复制已有覆盖。
- 计划的输入锁定到实际选中的材料名称，执行再分配 owner 的具体 `itemKey`。命名、组件变体不会借用其他 owner 的余额；当前允许普通配方消耗该 owner 自己的命名材料。
- 已有模板可作为自身复制配方种子，并按净增长计算触发次数。返还桶/瓶作为真实产出供后续步骤和配额模拟使用。

### 实物与结算

- 每次只取一个配方触发的输入，要求背包、光标、合成格和窗口处于可核对状态。历史背包物品不能混入本次原料。
- 取料使用登记槽位，不在无位置记录时盲搜，也不自动把未解释余量记给 `momo`。严格模式核对服务端箱子、背包和光标，拒绝错误窗口、过期包、缺包和服务端拒绝。
- 配方输入、数量、metadata、结果和 2×2/3×3 要求必须匹配 live registry；3×3 还验证真实工作台方块与距离。
- Mineflayer 会预测结果，故不能仅凭 `bot.craft` resolve 或本地背包变化结算。执行器要求独立服务端证据；未知返还物和不匹配结果进入恢复。
- 兼容完整窗口包的 `carriedItem`、现代 `set_cursor_item` 及旧光标槽位更新；最后点击后的空光标必须被服务端确认。现代协议省略背包预测回包时，仅在已有独立结果槽证据后，允许重开登记容器取得完整背包和空光标，再比较稳定状态；缺结果槽、缺完整包、错物或非空光标均拒绝结算。
- `craft_batches` 幂等键保护每次触发；扣原料、加全部产出、调整预留、写 `transactions` 和更新 journal 在一个 SQLite 事务提交。
- 内部取料/回库不再产生新存款。产物流水、原料流水和订单收尾使用云仓共用交易表，界面显示中文类型。
- 配额检查模拟每次触发后的暂态峰值，包含中间品、不可堆叠物及返还容器。实际仓满时保留已确认产物的归属和预留，不报成功。

### 中断与并发

- 在移动前保存物理基线；取料前及点击前分别持久化阶段和单次转换意图。
- 合成和恢复持有仓库锁。全局任务租约独立于 `worker.active`，死亡、注销和重连均不能提前释放仍在运行的网络 Promise。
- 恢复绑定原 `botId`，重连使用同一身份的新连接，不能改派另一台机器人的背包。新连接与复活流程等待旧执行排空后再核验。
- 永久停用时取消该机器人的排队恢复请求，避免 exclusive 任务卡住队首；journal 和资产占用仍保留。
- 有 pending journal 时，普通余额修改、同步、组织改名/删除、身份合并、物品键迁移及通用残留归属不能改写其资产。
- 最后一个 journal 安全结束后执行启动时延迟的物品键迁移和离线身份合并；失败保留待办，后续资产入口重试，仍失败时拒绝新资产操作。历史 journal 保留当时的精确键以供审计。
- 恢复重新读取登记容器及完整服务端背包/光标。只接受原料未转换或恰好一次已证明转换；可幂等补账，不能凭预测制造产物余额。

## 复审发现与处理

| 初始审查问题 | 最终处理 |
| --- | --- |
| 无 output/depositOperation 导致正常链路收尾失败 | 删除旧交付路径，直接由云仓严格回库收尾 |
| 实物变化未进余额、槽位与流水 | 精确取存快照 + 原子转换账本 |
| 按名称取料可偏离 owner 的具体变体 | 具体材料计划 + itemKey 分配和预留 |
| 排队计划过时、未预留 | 开工重新鉴权/规划并原子预留 |
| 崩溃残留走 momo | 持久 journal、恢复和通用残留保护 |
| 取消/超时只退出外层 Promise | 等原始操作排空，保留租约与不确定资产 |
| 盲搜上限和快照契约不一致 | 使用云仓登记槽位与快照，无独立 buffer/output 适配 |
| Olela vendor pathfinder 契约不匹配 | 删除复制的寻路层，复用云仓并验证工作台到达 |
| 配方版本与返还容器缺失 | live registry 配方、共享返还物定义 |
| 测试漏跑和 shim 静默漏注册 | 默认测试包含 craft，修复注册和 matcher |
| 中文入口、数量和超时配置不一致 | 接入目录解析、安全数量校验、配置预算 |
| 最后一轮恢复错机、漏重试、停用队首阻塞 | 绑定 botId、等待 drain、取消永久停用排队恢复 |
| 现代协议光标包和省略预测回包未覆盖 | 独立 raw 光标证据 + 有结果槽前提的完整服务端快照核验 |
| 恢复后延迟迁移漏执行、复活后队列未唤醒 | terminal 后迁移并保留失败重试；respawn 收尾主动 dispatch |
