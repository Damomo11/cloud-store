# 云仓库合成链路

本功能只使用云仓库已有的散装物品。原料、配方中间品、返还容器和成品都仍在云仓库登记的容器中；不建立 Olela 专用缓冲箱或成品箱。Olela 的 `CraftPlanner` 负责规划，云仓库的 `Warehouse` 负责实物取存，`ItemCatalog` 负责精确 `itemKey`，`CraftLedger` 负责归属、预留、转换流水与恢复记录。

## 请求与数量

- 系统管理员使用 `!合成 物品名 [目标数量]`。请求在执行机器人取得仓库独占锁后重新核验管理员和个人/组织仓库成员身份，并基于当时的可用余额重新规划。
- 目标数量表示仓库最终至少拥有的该物品数量，已有成品抵扣缺口；没有合成需求时不取料。
- 规划来源是 `server.version` 对应的 `minecraft-data` 普通有序/无序工作台配方。3×3 配方要求 `craft.table` 指向可到达的真实工作台。缺少散装材料时拒绝，不执行采集、熔炼、切石、锻造或盒内取料。
- 规划阶段按物品名称计算配方，执行阶段必须分配并预留该 owner 的具体 `itemKey` 和数量。不能使用其他 owner 的余额，也不能把未解释的余量自动记给 `momo`。

## 取货缺口预览

默认取货和 Web 下单共用缺口规划器。Web 提供只读接口 `POST /api/action/withdraw/plan`，校验登录、仓库权限和请求格式后返回当前可取分配、缺口以及合成候选，并附带当前活动任务状态。规划结果不创建 `inventory_reservations`，不扣库存账，也不持久化订单；它只是一次可能过期的库存快照。

个人默认取货的候选规划会沿用实际取货来源顺序，包含个人仓库和玩家已加入的组织仓库；正式取货仍只对实际分配到的物品建立预留，并在预留后重新计算候选，避免把同一份库存同时当作取货物品和合成原料。

`/api/litematic/plan` 保留 `selected` 和 `missing`，并增加统一的 `shortage`、`craft` 字段。`shortage` 说明请求量、可取量、缺口量和原因；`craft` 说明每个缺口的合成状态、候选计划或不可合成原因。个人默认仓库会沿用实际取货来源顺序检查组织仓库；显式组织仓库只检查该仓库。当前接口只返回合成候选，不自动执行合成。

合成候选按物品 ID 和单一仓库归属规划，精确 NBT/组件变体仍须在后续执行阶段重新核对，候选本身不会改变库存或账单。

正式取货开始后，服务会在仓库锁内重新计算分配并建立原有预留，再按扣除本次取货分配后的散装库存重新规划。预览结果不会直接用于扣账或执行。取货交付、`applyWithdrawDeduction`、`deductConfirmedMissing` 及预留生命周期继续遵循既有流程。

## 开工前的背包清理

机器人登录后沿用服务器上的实际背包，闲置时也可能拾取物品，因此不能假定登录或空闲就意味着空背包。合成在执行机器人的独占任务内先核验仓库归属和待恢复合成记录，再将普通背包残留回存云仓；清理完成后才重新规划、预留并开始合成。

清理复用普通存取任务的 `flushResidual()`：待完成的存货记回原 owner；尚未交付的取货只回存实物，不重复增加余额，已确认交付部分仍按原规则扣账；没有恢复记录可解释的物品沿用现有策略记入 `momo`，不会记给本次合成请求者。仓库满或清理失败时停止；同一服务实例内重试，会沿用已登记残留的跟踪记录，避免重复加账。

存在任何机器人的待恢复合成时，禁止普通清理；窗口、光标或个人合成格状态异常时也保持拒绝，不盲目关窗或丢弃物品。此类状态须按恢复流程或人工核对处理。清理期间取消、死亡或连接失效后，不会继续启动合成；在途清理操作仍须先排空。

清理在合成控制器取得仓库锁之前执行，因为存回操作会自行取得同一把不可重入锁。开工及每批完成后的严格空背包检查继续保留。

## 分批合成与背包容量

执行层以主背包和快捷栏共 **36 格**为空为前提，按堆叠上限计算每次触发的输入与全部产出占用，再确定一批能执行多少次触发；返还的桶、瓶等也计入产出。盔甲和副手不在这 36 格内，当前没有工具、食物等自用物品保留清单。规划只使用所选 owner 的仓库散装余额，不把机器人原有背包当作原料；`CraftPlanner.estimatedSlots` 是估算，实际批次由控制器限制，owner 的仓库额度另行核验。

每批只取出该批所需的原料，完成以下步骤并全部回存后再开始下一批；多步配方依次执行。

1. 在任何实物变化前持久化 `craft_operations` 操作与 `inventory_reservations`，记录 owner、机器人、目标、计划和精确原料。取料前记录全仓实物基线与 `withdrawing` 阶段。
2. 由 `Warehouse` 在仓库锁内取出预留的精确 `itemKey`。取存只改变容器槽位和背包，不改变 owner 余额。未能确认的容器转移保留操作和预留。
3. 取料确认后，记录 `crafting` 的批次意图：触发编号和次数、合成前背包、预计消耗和预计产出。返还的桶/瓶等容器也属于产出。
4. 执行标准 `bot.craft(recipe, triggers, table)`。配方输入、结果、工作台要求必须和计划一致；服务端结果槽、完整产物背包和空光标还须独立于客户端预测得到确认。如果现代协议省略了预测正确的背包更新，在已收到独立结果槽证据后，重开登记容器读取完整服务端背包及光标，再核对稳定状态；没有结果槽证据时不能使用这条确认路径。
5. `CraftLedger.confirm` 在一个 SQLite 事务中扣原料余额、加全部产出余额、调整预留、写转换流水与幂等批次。只有确认转换才改变 owner 余额。
6. 由 `Warehouse` 将背包里的产物和余料回存。只有容器和背包实物得到服务端确认、背包/光标/合成格清空后，才能进入 `ready` 并开始下一批。

`craft_batches` 的 `(operation_id, batch_key)` 防止同一已确认触发重复扣账或加账。任务中断后，余额与预留仍绑定原 owner；完成或证明原料已安全归仓后才释放预留。回库空间不足时保留 journal，不能把产物视为已交付，也不能将其转记 `momo`。

消耗、产出和订单收尾分别写入云仓原有 `transactions`，在交易记录中显示为“合成消耗”“合成产出”“合成订单”。这是物品转换流水；当前没有另设合成金币收费规则。

## 中断恢复

死亡、断线、超时、窗口异常或取存证据不足时，旧执行 Promise 和机器人任务占用必须等操作真正结束。不可确认的操作保留 `craft_operations`、预留及其物品归属，同时暂停普通资产写入、同步和残留自动归属。管理员向原执行机器人发送 `!合成恢复`。

恢复重新读取已登记容器及完整的服务端背包快照，并与持久化实物基线、合成前状态和预计转换逐项比较。只能在“原料未转换”或“单次转换已被独立证实”两种情况下回库；后一种情况可幂等补记转换。位置、数量、物品身份或光标有歧义时继续保持预留，交由人工核对，不强行清账。恢复成功表示中断订单已安全收尾，可以重新提交，并不表示原订单继续合成剩余触发。

恢复始终绑定原执行 `botId`；临时重连可由同一 `botId` 的新连接接续核验。新连接及死亡后的恢复先等待旧执行 Promise 结束；旧 Promise 永久不结束时保留占用，需要管理员处理连接或重启后核对。永久停用机器人会取消它排队中的恢复请求，待重新启用后再恢复。

启动时因待恢复合成而延迟的物品键迁移和离线身份合并，在最后一个 journal 结束后执行；失败保留待办，后续资产任务重试，迁移仍失败时拒绝新资产操作。

## 与原云仓问题的边界

本次改动只修复影响合成的共享边界：合成期间的身份/库存写保护、独占任务占用、精确预留、合成转换记账，以及取存和合成的服务端证据。原云仓普通存取、潜影盒拆装、未知盈亏分摊、`momo` 常规策略、订阅展示等既有行为不在本次 PR 的修复范围；它们不能接管仍有合成 journal 的资产。

离线测试覆盖规划版本、配方返还物、精确原料、真实 Mineflayer 合成插件的窗口交互、SQLite 转换/幂等、死亡与重连占用、仓满和恢复拒绝。上线前仍需在与 `server.version` 一致的测试服核验 2×2、3×3、返还容器、组织仓库、断线/死亡及仓满；本地测试不等于真服验收。
